# Эмулятор SNMP v2c-устройства

Одно виртуальное устройство с метриками в памяти и изменением значений по
сценарию независимо от запросов. Поддерживаются GET, GETNEXT и GETBULK.

## Запуск

Нужны Python 3.11–3.13 и `uv`. В `.python-version` закреплён Python 3.13,
в `uv.lock` — версии зависимостей.
Перед обновлением окружения или переустановкой пакета закройте GUI: Windows
блокирует замену запущенного `snmp-emulator-gui.exe`.

```bash
uv sync --locked
uv run --locked snmp-emulator --device-config examples/device.json --scenario examples/stable.json --check-config
uv run --locked snmp-emulator --device-config examples/device.json --scenario examples/cpu-step.json
```

`--check-config` проверяет оба файла и их связи, выводит
`configuration is valid: 5 metrics` и завершается без создания приложения и
открытия UDP-порта. Для JSON обязательны оба аргумента: `--device-config` и
`--scenario`. `--version` работает без них. `--log-level` принимает `DEBUG`,
`INFO`, `WARNING`, `ERROR`; по умолчанию используется `INFO`. Остановка — Ctrl+C.

Примеры слушают `127.0.0.1:1161`, повышенные права не требуются. Для доступа с
другого компьютера укажите подходящий адрес интерфейса или `0.0.0.0`.

## Графическая панель

Панель упрощает запуск и показ сценариев. GUI — дополнительный интерфейс,
выбранный для демонстрации; исходное ТЗ не требует графического интерфейса.

Нужны Python 3.11–3.13 с Tk и графическая сессия. На Windows установите обычный
Python с python.org с компонентом **Tcl/Tk and IDLE**. В Linux установите пакет
Tk для своей версии Python (например, `python3-tk` в Ubuntu). Tkinter входит в
поставку Python и не устанавливается через pip; дополнительных Python-зависимостей
для панели нет. Проверка установки: `python -m tkinter` открывает тестовое окно.

Из чистого окружения в каталоге проекта:

```powershell
uv sync --locked --python 3.13
uv run --locked snmp-emulator-gui
```

Если выбранный uv Python не содержит Tk, укажите путь к установленному Python
с Tk: `uv sync --locked --python C:\Python313\python.exe`. После установки
wheel или sdist командой `python -m pip install <путь-к-пакету>` доступны
`snmp-emulator-gui` и `python -m snmp_emulator.gui` из любого каталога.
Демонстрационные JSON-файлы устанавливаются вместе с пакетом.

Экран устроен последовательно: готовый пример или своя пара файлов →
запуск/остановка и состояние → текущие показатели → график числового показателя.
Это функциональная основа интерфейса; отдельная визуальная доработка отложена
и не является условием его работоспособности.

Для показа не нужно вводить OID или команды SNMP:

1. Выберите «Рост загрузки процессора» и нажмите «Запустить».
2. Таблица и график показывают рост `cpu_usage` с 15 до 90. В списке над графиком
   можно выбрать другой числовой показатель. Для «Скачка температуры» выберите
   «Температура»: через 5 секунд значение изменится с 35 до 80.
3. Адрес, UDP-порт и community берутся из устройства и отображаются под кнопками.
   После завершения сценария агент продолжает отвечать с последними значениями.
   Счётчик сценария останавливается на его длительности (например, `20 / 20 с`),
   а отдельный счётчик работы эмулятора продолжает расти. График после окончания
   сценария показывает сохранённое значение во времени работы эмулятора.
4. Нажмите «Остановить», выберите другой пример и запустите его. Новый запуск
   восстанавливает начальные значения. Закрытие окна также останавливает агент
   и освобождает порт; окно закрывается после завершения фоновой работы.

Два режима разделяют демонстрацию и работу со своими конфигурациями:
«Готовый пример» показывает только список демонстраций, «Свои JSON-файлы» —
пути устройства и сценария с кнопками «Выбрать файл…». Переключение режимов
сохраняет пользовательские пути; выбор примера их не перезаписывает.
Проверку любой пары выполняет общий `load_json_config`, как в CLI.
Название демонстрации внутри JSON не требуется.
Диалог выбора файла открывается в папке уже выбранного файла; по умолчанию
это каталог готовых устройств и сценариев `examples`. Если выбранная папка
недоступна, используется каталог примеров из установленного пакета или проекта.
Ошибки чтения, конфигурации и занятого порта отображаются в окне. Пока агент
работает, выбор профиля и повторный запуск заблокированы. Снимки значений
обновляются примерно каждые 100 мс; график хранит последние 600 снимков (около
60 секунд), поэтому при более частых изменениях не отображает каждый тик.
CLI и внешние SNMP-клиенты продолжают работать; для одновременного запуска
нескольких экземпляров нужны разные порты.

Для независимой проверки запущенной панели можно использовать команды GET/WALK
из раздела демонстрации ниже. Автоматические проверки жизненного цикла и
совпадения показателей с SNMP находятся в `tests/test_gui_controller.py`;
`tests/test_gui.py` проверяет настоящее окно. На Linux для этих окон нужен
дисплей или `xvfb-run -a`; CI запускает их с виртуальным дисплеем и не допускает
пропуска GUI-проверок. `tests/gui_smoke.py` проверяет окно и GET/WALK для
установленного пакета.

### Редактор конфигураций

Остановите эмулятор, если он запущен, и нажмите «Редактор конфигураций…».
Редактор открывает пару, выбранную в панели. Кнопка «Новая пара» начинает
создание с нуля, а «Открыть пару…» позволяет указать два других JSON-файла.
Для первого прогона выберите в панели пример «Рост загрузки процессора».

1. На вкладке «Устройство» задайте адрес, UDP-порт, community и метрики.
   У метрики указываются имя, OID, тип и начальное значение. Для аварийного
   старта задайте аварийные значения здесь или откройте `device-emergency.json`
   в паре с `recovery.json`.
2. На вкладке «Сценарий» задайте длительность и интервал обновления. В разделе
   «Изменения метрик» выберите OID и правило — постоянное значение, скачок,
   шаг до предела или последовательность значений. В примере с ростом CPU
   можно изменить предел `cpu_usage` с 90 на 60.
3. Чтобы смоделировать отключение, включите «Полная недоступность» и задайте
   её начало и длительность внутри сценария. В этом режиме значения метрик
   остаются постоянными. Режим ответа отдельной метрики задаётся в разделе
   «Доступность OID».
4. Нажмите «Сохранить для запуска…» и укажите два разных JSON-файла. Панель
   переключится в режим «Свои JSON-файлы» и подставит сохранённые пути.
   Нажмите «Запустить». Эту же пару можно снова открыть в редакторе.

Кнопка «Проверить» применяет те же правила, что и CLI, и показывает ошибки
рядом с полями. Сохранение доступно после исправления ошибок. При открытии
файла с неизвестным полем или типом правила редактор покажет сообщение,
а исходный файл сохранит своё содержимое.

### Готовые устройства

В каждом JSON-устройстве от 5 до 10 метрик, включая `Integer32` и `OctetString`.
Все примеры используют демонстрационные OID в ветке `1.3.6.1.4.1.55555`,
адрес `127.0.0.1:1161` и community `public`. Это учебные профили, а не MIB
конкретных производителей. Одновременно на одном порту запускается один профиль.

| Устройство | Метрик | Устройство JSON | Сценарий JSON | Показ |
|---|---:|---|---|---|
| device · 5 метрик | 5 | `examples/device.json` | `stable.json`, `temperature-jump.json`, `cpu-step.json` | Стабильные значения, скачок температуры, рост CPU |
| device · 7 метрик | 7 | `examples/device-7.json` | `examples/traffic-growth.json` | Рост входящего/исходящего трафика и загрузки CPU |
| device · 8 метрик | 8 | `examples/device-8.json` | `examples/load-growth.json` | Рост нагрузки, температуры и трафика |
| device · 10 метрик | 10 | `examples/device-10.json` | `examples/variable-load.json` | Два пика нагрузки, спад и охлаждение |
| device · 6 метрик | 6 | `examples/device-emergency.json` | `examples/recovery.json` | Независимое восстановление из аварийного состояния |

У device с 7 метриками доступны CPU, температура, описание, число портов, активные
порты, входящий и исходящий трафик. За первые 9 секунд CPU повышается с 25 до
70%, трафик — со 120 до 600 и с 80 до 440 Мбит/с. Остальные показатели
сохраняются. Сценарий длится 20 секунд с интервалом 1 секунда.

У device с 8 метриками доступны CPU, память, температура, активные порты,
входящий и исходящий трафик, описание и состояние. Каждые 2 секунды CPU
растёт с 15 до 85%, память — с 35 до 70%, температура — с 35 до 63 °C,
трафик — со 100 до 520 и с 80 до 360 Мбит/с. Пределы достигаются через
14 секунд; на 10-й секунде состояние меняется с `OK` на `busy`. Полная
длительность — 20 секунд. Изменения заданы отдельными правилами сценария;
автоматическая физическая зависимость между метриками не моделируется.

Все профили доступны в режиме «Готовый пример». В консоли OID и имена
метрик подсказываются из выбранного устройства. После завершения сценария
последние значения остаются доступны по SNMP до остановки.

Запуск из CLI:

```powershell
uv run --locked snmp-emulator --device-config examples/device-7.json --scenario examples/traffic-growth.json
uv run --locked snmp-emulator --device-config examples/device-8.json --scenario examples/load-growth.json
uv run --locked snmp-emulator --device-config examples/device-10.json --scenario examples/variable-load.json
```

Команды запускаются по очереди. Перед следующим запуском остановите предыдущий через Ctrl+C.

### Переменная нагрузка

Выберите «device · 10 метрик · Переменная нагрузка». Прогон длится 54 секунды,
значения обновляются каждые 3 секунды. CPU достигает 64% на 12-й секунде,
снижается до 26% на 24-й и растёт до 79% на 36-й. Входящий трафик во время
второго пика достигает 560 Мбит/с. Температура достигает максимума 53 °C на
42-й секунде, когда загрузка CPU уже снижается. Активные потоки, использование
памяти, исходящий трафик и скорость потери пакетов тоже меняются. Число активных
портов и описание устройства постоянны. Все значения заданы в сценарии.

В окне «SNMP-запросы…» команда `WALK 1.3.6.1.4.1.55555.5` читает все десять
метрик, а `GET cpu_usage` — текущую загрузку CPU.

### Независимое восстановление

Восстановление запускается сразу из аварийной конфигурации, без предварительного
сценария деградации:

```powershell
uv run --locked snmp-emulator --device-config examples/device-emergency.json --scenario examples/recovery.json --check-config
uv run --locked snmp-emulator --device-config examples/device-emergency.json --scenario examples/recovery.json
```

В панели выберите «Готовый пример» → «device · 6 метрик · Восстановление» и
нажмите «Запустить». В режиме «Свои JSON-файлы» можно выбрать ту же пару.
Сценарий длится 12 секунд, интервал обновления — 1 секунда.

| Метрика | OID | Начальное значение | Восстановление |
|---|---|---|---|
| CPU | `1.3.6.1.4.1.55555.4.1.0` | 95% | −10 каждую секунду до 15% на 8-й секунде |
| Температура | `1.3.6.1.4.1.55555.4.2.0` | 80 °C | −5 каждую секунду до 35 °C на 9-й секунде |
| Описание | `1.3.6.1.4.1.55555.4.3.0` | `SNMP demo device` | Сохраняется |
| Память | `1.3.6.1.4.1.55555.4.4.0` | 40% | Сохраняется |
| Интерфейс | `1.3.6.1.4.1.55555.4.5.0` | `down` | `up` на 10-й секунде |
| Ошибки интерфейса | `1.3.6.1.4.1.55555.4.6.0` | 120 | Сохраняются, рост прекращён |

Все числовые метрики имеют тип `Integer32`, описание и состояние интерфейса —
`OctetString`. Соответствующий нормальный профиль `examples/device-normal.json`
содержит те же имена, OID и типы: CPU 15%, температура 35 °C, интерфейс `up`,
ошибки 0. Восстановление сохраняет накопленные 120 ошибок, не обнуляя счётчик.

После завершения последние значения доступны до остановки. Для повтора
остановите эмулятор через Ctrl+C или «Остановить» и запустите ту же пару:
она снова начнётся с CPU 95%, температуры 80 °C, `down` и 120 ошибок.
Устройства и сценарий используют существующий JSON-формат.

Проверка внешним клиентом:

```bash
snmpget -v2c -c public -On 127.0.0.1:1161 1.3.6.1.4.1.55555.4.1.0 1.3.6.1.4.1.55555.4.2.0 1.3.6.1.4.1.55555.4.5.0 1.3.6.1.4.1.55555.4.6.0
snmpwalk -v2c -c public -On 127.0.0.1:1161 1.3.6.1.4.1.55555.4
```

Встроенная консоль принимает `GET cpu_usage`, `GET interface_status`,
`GET interface_errors` и `WALK 1.3.6.1.4.1.55555.4`.

### Показ SNMP-запросов

Нажмите **«SNMP-запросы…»**, чтобы открыть отдельную консоль. Она отправляет
SNMP v2c-пакеты по UDP на адрес и порт запущенного устройства, используя его
community. Для `0.0.0.0` клиент обращается к `127.0.0.1`. Встроенная консоль
готова к работе после запуска панели. Для независимой проверки можно использовать
внешний SNMP-клиент.

Кнопки **GET**, **GETNEXT**, **WALK**, **GETBULK**, **HELP** и **CLEAR** подставляют
готовую команду. Для SNMP подставляется OID текущей конфигурации. Нажмите Enter,
Enter на цифровой клавиатуре или «Выполнить». При остановленном эмуляторе
консоль предложит запустить его и сохранит сетевую команду в поле ввода.
Локальные команды HELP и CLEAR работают в любом состоянии.
При наведении на кнопку шаблона появляется подсказка о назначении команды.
После успешной отправки поле ввода очищается; команда доступна через ↑/↓.
Ошибочная команда остаётся в поле для исправления. Крестик рядом с полем
очищает только ввод, сохраняя вывод и историю команд. `CLEAR` очищает вывод.

| Команда | Что демонстрирует |
|---|---|
| `GET cpu_usage` | Значение конкретной метрики по имени или её OID |
| `GETNEXT 1.3.6.1.4.1.55555.1` | Первую метрику после указанного OID |
| `WALK 1.3.6.1.4.1.55555.1` | Обход ветки последовательными GETNEXT |
| `GETBULK 1.3.6.1.4.1.55555.1 5` | До пяти следующих значений одним GETBULK, non-repeaters=0 |

В SNMP нет отдельной операции GETWALK: WALK — процедура клиента. Для удобства
принимается псевдоним `GETWALK`. Также доступны `snmpget`, `snmpgetnext`,
`snmpwalk`, `snmpbulkget` с тем же коротким синтаксисом; параметры оболочки
Net-SNMP (`-v`, `-c` и другие) здесь не используются.

При вводе команды список под строкой предлагает доступные OID и имена метрик
из работающего устройства. Можно нажать на подсказку или вставить первую
клавишей Tab. В пустой строке список предлагает все шесть основных команд;
после GET/GETNEXT/WALK/GETBULK — подходящие OID. Он показывает четыре строки
за раз и прокручивается колёсиком или вертикальной полосой справа; остальные
подсказки не отбрасываются. ↑/↓ в строке ввода возвращают предыдущие команды.
OID допускается ввести
вручную: например, `GET 1.3.6.1.4.1.55555.99.0` показывает стандартный ответ
`NoSuchObject`, GETNEXT после последней метрики — `EndOfMibView`.
В ответе выводятся OID, тип, значение, адрес назначения и длительность запроса.
`HELP` выводит справку, `CLEAR` очищает видимую историю ответов.
Остановка и повторный запуск не стирают предыдущие ответы: консоль добавляет
отметки времени, номер сеанса, имена файлов профиля и сообщения о состоянии.
Номер сеанса увеличивается при каждом новом запуске, в том числе при запуске
того же профиля. Если запрос предыдущего сеанса ещё завершается, новый запуск
доступен после его окончания или отмены, чтобы ответы не смешивались.

Запросы выполняются в фоне. «Отменить» прерывает обход; таймаут одного ответа —
1 секунда без повторов, общее ограничение — 15 секунд, WALK — до 256 метрик,
GETBULK — от 1 до 50 повторений (по умолчанию 5). Закрытие окна консоли
отменяет запрос и сохраняет историю до закрытия приложения. Остановка агента
и закрытие главного окна также отменяют запрос; приложение дожидается
завершения сетевого клиента. Консоль показывает ответы сети, таблица и график
основной панели — снимки хранилища; значения могут различаться, если между
обновлением таблицы и запросом произошёл следующий тик сценария.

## Формат устройства

Оба файла — UTF-8 JSON без BOM. В `agent` задаются IPv4-адрес `host`, UDP-порт
`port` (1–65535, по умолчанию 1161) и непустая строка `community`. Если поля
пропущены, используются `0.0.0.0`, `1161`, `public`. Объект `agent` обязателен.

```json
{
  "agent": {"host": "127.0.0.1", "port": 1161, "community": "public"},
  "metrics": [
    {"name": "cpu", "oid": "1.3.6.1.4.1.55555.1.1.0", "type": "Integer32", "initial": 15},
    {"name": "status", "oid": "1.3.6.1.4.1.55555.1.2.0", "type": "OctetString", "initial": "OK"}
  ]
}
```

У метрики обязательны `name`, `oid`, `type`, `initial`. Необязательное поле
`access` допускает только `read-only`. Имена после удаления крайних пробелов
должны быть непустыми и уникальными. OID — числовые компоненты, разделённые
точками; разрешена одна начальная точка. Начальная точка и ведущие нули
нормализуются, поэтому `.01.3.6` и `1.3.6` считаются одним OID.

`Integer32` имеет диапазон −2147483648…2147483647. Старое имя `Integer`
принимается как псевдоним того же типа; проверка и кодирование SNMP общие.
`OctetString` принимает строку UTF-8, максимум 65535 байт. Сохраняются типы
`ObjectIdentifier`, `IpAddress`, `Counter32`, `Gauge32`, `TimeTicks`, `Counter64`.
Числовые строки, дробные и логические значения не заменяют целое число.

## Формат сценария

```json
{
  "duration": 20,
  "update_interval": 1,
  "rules": [
    {"type": "step", "oid": "1.3.6.1.4.1.55555.1.1.0", "step": 10, "limit": 90}
  ]
}
```

`duration` и `update_interval` — положительные конечные числа в секундах.
В `rules` нужна хотя бы одна запись. Каждое правило ссылается на метрику по
нормализованному `oid`; на один OID допускается одно правило. Метрики без
правил сохраняют `initial`.

| `type` | Остальные поля | Поведение |
|---|---|---|
| `constant` | `value` | Устанавливает значение при старте и сохраняет его |
| `jump` | `at`, `value` | Сохраняет `initial` до `at`, затем устанавливает `value` |
| `step` | `step`, `limit` | Начинает с `initial`, каждый интервал прибавляет шаг и ограничивает результат пределом |
| `sequence` | `values` | Берёт первое значение на нулевом тике, затем по одному значению за интервал и удерживает последнее до конца сценария |

`constant` и `jump` принимают значения целевого SNMP-типа, включая строки.
Для `jump` требуется `0 <= at <= duration`. `step` предназначен для числовых
метрик: шаг — ненулевое целое число, предел должен лежать по направлению шага
от начального значения и внутри диапазона типа. Отрицательный шаг поддержан,
например `step: -3, limit: -1` при `initial: 10` даёт 10, 7, 4, 1, −1, −1.
У `sequence` список `values` должен содержать хотя бы одно значение. Все значения
проверяются по типу метрики. Применяются только значения, чьи тики попадают в
пределы длительности сценария.

Обновления выполняются в моменты `0`, `update_interval`, `2 * update_interval`
и далее до `duration` включительно. Скачок между тиками применяется на первом
тике, не меньшем `at`. Если такого тика до конца сценария нет, значение не
меняется. Если длительность не кратна интервалу, сохраняется результат
последнего полного тика. Например, при длительности 0.35 и интервале 0.1
последний тик — 0.3. Расчёт опирается на монотонное время и десятичную
арифметику; задержки планировщика не накапливаются. При задержке выполняется
актуальный тик без воспроизведения промежуточных состояний.

После `duration` сценарий прекращает обновления, но агент продолжает отвечать
с последними значениями до остановки процесса. Новый запуск загружает `initial`.

Неизвестные поля, повторные JSON-ключи, дубли имён/OID, неверные типы, значения,
правила и ссылки отклоняются до создания приложения. Ошибки чтения, UTF-8,
JSON и конфигурации завершают CLI кодом 2 с диагностикой без traceback.

## Демонстрация

`examples/device.json` содержит пять метрик: CPU=15, температура=35,
описание устройства, память=40 и статус=OK. Запускайте по одному сценарию:

```bash
uv run --locked snmp-emulator --device-config examples/device.json --scenario examples/stable.json
uv run --locked snmp-emulator --device-config examples/device.json --scenario examples/temperature-jump.json
uv run --locked snmp-emulator --device-config examples/device.json --scenario examples/cpu-step.json
```

| Сценарий | Ожидаемый результат |
|---|---|
| `stable.json` | Все значения постоянны, длительность 30 с |
| `temperature-jump.json` | Температура 35 → 80 на 5-й секунде, длительность 20 с |
| `cpu-step.json` | CPU 15, 25, 35, …, 85, 90 с шагом раз в секунду; 90 с 8-й секунды, длительность 20 с |

В другом терминале используйте Net-SNMP (`snmpget`, `snmpwalk`):

```bash
snmpget -v2c -c public -On 127.0.0.1:1161 1.3.6.1.4.1.55555.1.1.0
snmpget -v2c -c public -On 127.0.0.1:1161 1.3.6.1.4.1.55555.1.2.0
snmpwalk -v2c -c public -On 127.0.0.1:1161 1.3.6.1.4.1.55555
snmpget -v2c -c public -On 127.0.0.1:1161 1.3.6.1.4.1.55555.99.0
```

GET возвращает `INTEGER: 15` для начального CPU и `INTEGER: 35` для температуры;
повторите запрос после указанного времени. WALK возвращает пять OID.
Неизвестный OID возвращает `No Such Object`, после последнего OID GETNEXT
возвращает `endOfMibView`. После 20 с CPU/температура сохраняют последнее значение.
Остановите процесс, запустите его снова и сразу запросите метрики: начальные
значения восстановятся. Неверная community приводит к тайм-ауту.

## Совместимость с YAML

## Журналирование

CLI и GUI используют стандартный `logging`. Журнал настраивается до загрузки
конфигурации и выводится в stderr. Формат записи: время, уровень, имя модуля и
сообщение. Например:

```text
2026-11-19 16:45:00,123 INFO snmp_emulator.application: listening on udp://127.0.0.1:1161
2026-11-19 16:45:01,123 INFO snmp_emulator.scenarios.engine: metric cpu_usage oid=1.3.6.1.4.1.55555.1.1.0 changed: 15 -> 20 (scenario=json)
2026-11-19 16:45:02,123 INFO snmp_emulator.application: emulator stopped
```

Для каждой метрики сравниваются значения в начале и конце тика. Изменение
`10 → 20 → 30` внутри одного тика создаёт одну запись `10 → 30`, а
`10 → 20 → 10` не создаёт записей. Начальная загрузка и повторная установка того
же значения не журналируются. Если правило меняет начальное значение на первом
тике, это изменение попадает в журнал. Для YAML указывается имя сценария, для
JSON — внутреннее имя `json`. Сброс значений при повторении YAML-сценария
учитывается вместе с остальными изменениями тика.

В CLI уровень выбирается через `--log-level`:

| Уровень | Какие сообщения видны |
|---|---|
| `DEBUG` | Все сообщения, включая отладочную диагностику |
| `INFO` | Изменения метрик, запуск, остановка, предупреждения и ошибки; по умолчанию |
| `WARNING` | Предупреждения и ошибки |
| `ERROR` | Ошибки конфигурации, запуска и выполнения |

Чтобы сохранить журнал CLI в файл:

```bash
uv run --locked snmp-emulator --device-config examples/device.json --scenario examples/cpu-step.json --log-level INFO 2> emulator.log
```

GUI использует уровень `INFO`. Для просмотра его журнала запустите панель из
терминала командой `uv run --locked python -m snmp_emulator.gui`. При запуске
через оконный `snmp-emulator-gui` на Windows консоль может быть недоступна.
Ошибки конфигурации и запуска также остаются видны в панели.

Ошибки чтения, UTF-8, синтаксиса, схемы и связей конфигурации записываются с
уровнем `ERROR`. CLI завершается с кодом 2. При ошибке преобразования значения
YAML журнал указывает файл, строку и столбец. Ошибка открытия UDP-порта содержит
адрес, порт и причину. CLI в этом случае завершается с кодом 1. Для ожидаемых
ошибок CLI выводит диагностическое сообщение без traceback. При неожиданной
ошибке выполнения traceback сохраняется для диагностики.
Успешные запуск и остановка записываются по одному разу; завершение сценария
само по себе не останавливает SNMP-агент.

### Журнал входящих SNMP-запросов

Общий UDP-агент (CLI и GUI) регистрирует каждый полученный SNMPv2c GET,
GETNEXT или GETBULK с корректной community. Один GETBULK считается одним
запросом; повторная датаграмма с тем же `request-id` получает собственный
`token` и отдельную пару событий. Неавторизованные и неподдерживаемые
запросы не учитываются. **Community и её значение никогда не записываются.**

События `snmp_request` создаются в журнале уровня INFO:

- `event=received`: `token`, время UTC (`time`), `source` (IP и порт),
  `pdu`, `request_id`, перечень `oids` из запроса.
- `event=result`: тот же `token`, адрес, тип и ID запроса,
  `outcome=sent|not_sent`, `error_status` и `error_index` итогового
  ответа, исключения отдельных привязок `exceptions` (OID и тип
  `noSuchObject`, `noSuchInstance`, `endOfMibView`), `reason`.
  Статус кодируется числом SNMP (например, `1` означает `tooBig`).
  Тире означает отсутствие поля.

Пример (номера, адрес и время приведены для иллюстрации):

```text
2026-11-23 10:00:00,000 INFO snmp_emulator.adapters.request_audit: snmp_request event=received token=1 time=2026-11-23T10:00:00+00:00 source=127.0.0.1:51000 pdu=GET request_id=71 oids=1.3.6.1.4.1.55555.99.0
2026-11-23 10:00:00,001 INFO snmp_emulator.adapters.request_audit: snmp_request event=result token=1 source=127.0.0.1:51000 pdu=GET request_id=71 outcome=sent error_status=0 error_index=0 exceptions=1.3.6.1.4.1.55555.99.0:noSuchObject reason=-
```

`sent` означает, что сформированный ответ был передан UDP-транспорту,
а не что удалённый клиент подтвердил получение (UDP не предоставляет
подтверждений). `not_sent` означает известную причину отсутствия передачи:
`transport_send_failed` при ошибке передачи, `agent_stopped` при остановке
с необработанным запросом или `pending_limit` при переполнении ограниченной
очереди. При штатном перезапуске очередь очищается, старые записи не
воспроизводятся. Для отслеживания дублирующихся ID используются адрес
отправителя и отдельный токен, но одна и та же community не включается
ни в ключ, ни в журнал.

## Ограничения

SNMP SET, traps, SNMP v3, импорт MIB и несколько устройств в одном процессе
не поддерживаются.


### Сценарий полной недоступности устройства (задача 08)

Добавьте необязательный объект `unavailability` в JSON-сценарий:

```json
{
  "duration": 6.0,
  "update_interval": 0.1,
  "rules": [],
  "unavailability": {"at": 2.0, "duration": 2.0}
}
```

См. готовый `examples/device-unavailability.json` (используется вместе с
`examples/device-normal.json`). В первые 2 секунды агент отвечает обычно,
с 2 до 4 секунд принимает GET/GETNEXT/GETBULK, но не отвечает; после
4 секунд ответы автоматически восстанавливаются. Клиент видит реальный
UDP timeout, а не SNMP error-status. Значения метрик остаются неизменными.
Если задана недоступность, правила изменения метрик, кроме `constant`,
запрещены; длительность недоступности обязана помещаться в `duration`.
Агент не закрывает сокет и продолжает журналировать входящие корректные
запросы (событие `outcome=not_sent reason=device_unavailable`) без
раскрытия community. Переходы доступности журналируются; в GUI появляется
отдельное состояние «Устройство временно недоступно». Прерывание или
повторный запуск не переносит недоступность в следующую сессию.

### Частичная недоступность отдельных OID (задача 09)

В JSON-сценарии можно задать необязательный массив `oid_responses`:

```json
{
  "duration": 8,
  "update_interval": 0.1,
  "rules": [],
  "oid_responses": [
    {"oid": "1.3.6.1.4.1.55555.4.2.0", "mode": "noSuchObject"},
    {"oid": "1.3.6.1.4.1.55555.4.3.0", "mode": "noSuchInstance"},
    {"oid": "1.3.6.1.4.1.55555.4.5.0", "mode": "genErr"}
  ]
}
```

Готовый пример: `examples/device-normal.json` +
`examples/partial-oid-unavailability.json`. Эти режимы задают поведение
точно указанного OID: `normal` (обычное значение), `noSuchObject`
(объект отсутствует), `noSuchInstance` (отсутствует экземпляр) и `genErr`
(ошибка обработки с ненулевыми `error-status` и `error-index`).
Неуказанные OID остаются доступными; неизвестный объект возвращает
`noSuchObject`, а отсутствующий экземпляр известного скаляра —
`noSuchInstance`.

GET сохраняет значения доступных OID даже в смешанном запросе с исключениями.
При `genErr` весь запрос получает PDU с `error-status=genErr` и
индексом проблемной исходной переменной (считая с 1). GETNEXT и GETBULK
пропускают отсутствующие OID при лексикографическом обходе, а при попадании
на режим `genErr` отвечают соответствующей ошибкой. Обычное
`endOfMibView` по-прежнему возвращается в конце доступных OID.

Каждый режим проверяется при загрузке: повторяющиеся, неизвестные и
некорректные OID, а также неподдерживаемые имена режимов отклоняются.
Режимы действуют и в CLI, и в GUI; журнал входящих запросов отражает
исключения и ошибки обработки раздельно. Значение community не журналируется.

## JSON-отчёт о прогоне (задача 10)

После остановки CLI или GUI сохраняет отдельный JSON-отчёт в `reports/`
в текущем каталоге запуска. Имя содержит исходное имя сценария и UTC-время,
чтобы разные прогоны не перезаписывали друг друга. В CLI путь можно указать
явно: `snmp-emulator --device-config examples/device.json --scenario
examples/stable.json --report-file ./run.json`. YAML использует имя
исходного YAML-файла. Путь отчёта должен отличаться от путей входных файлов.
Команда `--check-config` отчёт не создаёт.

Отчёт содержит идентификатор сценария, параметры и конфигурацию **без community**,
UTC-время начала и окончания, длительность, начальные и конечные значения,
счётчики принятых GET/GETNEXT/GETBULK, отправленных ответов,
преднамеренно подавленных запросов, фактически смоделированных `genErr`
(не иных ошибок со статусом `genErr`), исключений
`noSuchObject` и `noSuchInstance`, ошибки и итог выполнения:
`completed`, `stopped_early` или `failed`. Завершение времени сценария
не останавливает агент; отчёт формируется при остановке приложения.
Сбор статистики идёт напрямую при обработке SNMP и не требует разбора логов.
Сохраняются только счётчики и ограниченный список ошибок, не все запросы.
Файл записывается через временный файл с атомарной заменой; ошибки записи
сообщаются в журнале и в GUI.
После успешного сохранения панель показывает итог прогона и полный путь к
отчёту. Кнопка «Открыть папку» открывает каталог отчёта.

## Демонстрационный комплект из пяти независимых сценариев (задача 11)

Для демонстрации расширенного учебного ТЗ используется **одно устройство с шестью
метриками**, два согласованных стартовых состояния и пять независимо запускаемых
пар JSON. Выполнять деградацию перед восстановлением **не нужно**: каждый запуск
создаёт новый набор значений из выбранного файла устройства. После окончания
сценария SNMP-агент продолжает отвечать с последними значениями, пока его не
остановят; при новом запуске значения снова берутся из конфигурации.

### Метрики учебного устройства

Все OID принадлежат **условному тестовому пространству**
`1.3.6.1.4.1.55555.4`; они **не являются** MIB конкретного производителя.
Тестовый enterprise ID используется только для демонстрации, не следует считать
его официально выделенным проекту.

| OID (полный суффикс к `1.3.6.1.4.1.55555.4`) | Метрика | SNMP-тип | Единица / значения | Норма → авария |
| --- | --- | --- | --- | --- |
| `.1.0` | `cpu_usage` | Integer32 | % | 15 → 95 |
| `.2.0` | `temperature` | Integer32 | °C | 35 → 80 |
| `.3.0` | `description` | OctetString | строка | SNMP demo device |
| `.4.0` | `memory_usage` | Integer32 | % | 40 → 85 |
| `.5.0` | `interface_status` | OctetString | `up` / `down` | up → down |
| `.6.0` | `interface_errors` | Integer32 | условный накопленный счётчик | 0 → 120 |

Состояние интерфейса демонстрируется строкой `up/down`, а не стандартной
MIB-переменной `ifOperStatus`. Для настройки UserGate используйте
перечисленные конкретные OID и типы, не предполагая наличия стандартных MIB.

| 4.1 Норма | `device-normal.json` | `demo-normal.json` | Все значения постоянны: 15/35/40/up/0 |
| 4.2 Деградация | `device-normal.json` | `demo-degradation.json` | CPU 15→95%, память 40→85%, температура 35→80°C, ошибки 0→120, интерфейс `down` на 9-й секунде |
| 4.3 Восстановление | `device-emergency.json` | `recovery.json` | CPU 95→15%, память 85→40%, температура 80→35°C, интерфейс `up` на 10-й секунде; накопленные ошибки остаются 120 и не растут |
| 4.4 Полная недоступность | `device-normal.json` | `device-unavailability.json` | Первые 2 с ответы есть, 2–4 с нет SNMP-ответов (timeout), после 4 с ответы восстановлены, значения не меняются |
| 4.5 Частичная недоступность | `device-normal.json` | `partial-oid-unavailability.json` | CPU, память и ошибки доступны; температура → `noSuchObject`, описание → `noSuchInstance`, статус интерфейса → `genErr` при запросе с корректным `error-index` |

Запуск любого сценария из корня репозитория (здесь пример деградации):

```bash
python -m snmp_emulator --device-config examples/device-normal.json --scenario examples/demo-degradation.json
```

Опрос из **другого терминала** (Net-SNMP):

```bash
snmpget -v2c -c public -On 127.0.0.1:1161 1.3.6.1.4.1.55555.4.1.0
snmpwalk -v2c -c public -On 127.0.0.1:1161 1.3.6.1.4.1.55555.4
```

Чтобы запустить следующий сценарий, остановите текущий (Ctrl+C) и подставьте
другую пару из таблицы. Порт `1161/UDP` и community `public` — **локальные
демонстрационные значения**. Для VM настройте доступный IP, firewall и
community с учётом сети; для UserGate источником данных остаётся SNMP-опрос.

**GUI:** все пять пар представлены в списке профилей с пометкой «Демо ТЗ».
Тесты `tests/test_demo_kit.py` проверяют реальные SNMP-ответы в ключевые
моменты; `tests/installed_smoke.py` проверяет комплект после установки
wheel/sdist. Проверки не заменяют фактическое подключение UserGate.

## Развёртывание на Ubuntu 24.04 LTS и подключение UserGate

### Установка и запуск без графической сессии

Скачайте wheel нужной версии в пустой рабочий каталог и выполните из него:

```bash
sudo apt-get update
sudo apt-get install python3-venv snmp
python3 -m venv .venv
.venv/bin/python -m pip install ./snmp_v2c_emulator-*.whl
.venv/bin/python -m pip check
.venv/bin/snmp-emulator --version
cp -r .venv/share/snmp-v2c-emulator/examples .
.venv/bin/snmp-emulator --device-config examples/device-normal.json \
  --scenario examples/demo-normal.json --check-config
.venv/bin/snmp-emulator --device-config examples/device-normal.json \
  --scenario examples/demo-normal.json --report-file reports/demo-normal.json
```

Для выпуска без приложенного wheel его можно собрать из архива исходников
через `python -m build --wheel` в отдельном окружении с пакетом `build`.
Полный CI на Ubuntu 24.04 проверяет установку и опрос установленного wheel
без графической сессии. После успешной проверки wheel доступен как артефакт
`verified-wheel` в полном прогоне для ветки: его можно скачать, распаковать
и приложить к выпуску, сверив версию пакета и коммит выпуска.

Пока процесс работает, в другом терминале выполните:

```bash
snmpget -v2c -c public -On -t 1 -r 0 \
  udp:127.0.0.1:1161 1.3.6.1.4.1.55555.4.1.0
```

Ожидается `INTEGER: 15`. Остановите эмулятор через Ctrl+C и проверьте отчёт
командой `.venv/bin/python -m json.tool reports/demo-normal.json`.
Если остановить процесс до окончания сценария, итогом будет `stopped_early`.

### Доступ из SIEM и LogAn

1. В копиях обоих стартовых профилей задайте в `agent.host` адрес сетевого
   интерфейса Ubuntu, доступный с сервера UserGate. Укажите свой `agent.community`
   из латинских букв и цифр. Если между узлами действует firewall, разрешите
   входящий трафик на `1161/UDP` с IP сервера UserGate. Сначала проверьте
   тот же адрес через Net-SNMP из сети опрашивающего узла.
2. В SIEM и LogAn добавьте сенсор в разделе «Сенсоры SNMP». Укажите IP Ubuntu,
   порт `1161`, SNMP v2 и community из профиля. Добавьте числовые OID и
   соответствующие SNMP-типы из таблицы метрик выше. Порядок ввода зависит от
   версии продукта. Сверьтесь с руководством для своего выпуска:
   [SIEM](https://docs.usergate.com/sensory-687/) и
   [LogAn](https://docs.usergate.com/sensory-347/).
3. Запустите пять пар по очереди. Для деградации и восстановления наблюдайте
   промежуточные значения и конечное состояние. Для полной недоступности
   зафиксируйте хотя бы один успешный опрос до окна, один пропущенный опрос
   в окне и успешный опрос после. Если окно в две секунды короче интервала
   опроса, используйте копию сценария с увеличенными `at`, `duration`
   окна и общей длительностью. Для частичной недоступности отметьте, что
   продукт показывает для доступных OID, отсутствующих значений и ошибки
   счётчика. Если интерфейс сводит ответы к одному статусу, проверьте
   детали через Net-SNMP и журнал запросов эмулятора.
4. После каждого прогона остановите CLI и сохраните отдельный JSON-отчёт.
   Сверьте значения, счётчики запросов и итог прогона с наблюдениями сенсора.
   Для полной недоступности проверьте `intentionally_suppressed`, для
   частичной — `no_such_object`, `no_such_instance` и `simulated_errors`.
   Конкретные счётчики зависят от запросов клиента.

При проверке на стенде зафиксируйте версию и сборку каждой системы UserGate,
версию эмулятора, интервал опроса, наблюдения по всем пяти профилям и пути
к отчётам. Фактические прогоны в SIEM и LogAn ожидают доступного стенда.
