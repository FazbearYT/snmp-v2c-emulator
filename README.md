# Эмулятор SNMP v2c-устройства

Одно виртуальное устройство с метриками в памяти и изменением значений по
сценарию независимо от запросов. Поддерживаются GET, GETNEXT и GETBULK.

## Запуск

Нужны Python 3.11–3.13 и `uv`. В `.python-version` закреплён Python 3.13,
в `uv.lock` — версии зависимостей.

```bash
uv sync --locked
uv run --locked snmp-emulator --device-config examples/device.json --scenario examples/stable.json --check-config
uv run --locked snmp-emulator --device-config examples/device.json --scenario examples/cpu-step.json
```

`--check-config` проверяет оба файла и их связи, выводит
`configuration is valid: 5 metrics` и завершается без создания приложения и
открытия UDP-порта. Для JSON обязательны оба аргумента: `--device-config` и
`--scenario`. `--version` работает без них. `--log-level` принимает `DEBUG`,
`INFO`, `WARNING`, `ERROR`; по умолчанию используется `INFO`. Остановка — Ctrl+C.

Примеры слушают `127.0.0.1:1161`, повышенные права не требуются. Для доступа с
другого компьютера укажите подходящий адрес интерфейса или `0.0.0.0`.

## Графическая панель

Панель упрощает запуск и показ сценариев. GUI — дополнительный интерфейс,
выбранный для демонстрации; исходное ТЗ не требует графического интерфейса.

Нужны Python 3.11–3.13 с Tk и графическая сессия. На Windows установите обычный
Python с python.org с компонентом **Tcl/Tk and IDLE**. В Linux установите пакет
Tk для своей версии Python (например, `python3-tk` в Ubuntu). Tkinter входит в
поставку Python и не устанавливается через pip; дополнительных Python-зависимостей
для панели нет. Проверка установки: `python -m tkinter` открывает тестовое окно.

Из чистого окружения в каталоге проекта:

```powershell
uv sync --locked --python 3.13
uv run --locked snmp-emulator-gui
```

Если выбранный uv Python не содержит Tk, укажите путь к установленному Python
с Tk: `uv sync --locked --python C:\Python313\python.exe`. После установки
wheel или sdist командой `python -m pip install <путь-к-пакету>` доступны
`snmp-emulator-gui` и `python -m snmp_emulator.gui` из любого каталога.
Демонстрационные JSON-файлы устанавливаются вместе с пакетом.

Экран устроен последовательно: готовый пример или своя пара файлов →
запуск/остановка и состояние → текущие показатели → график числового показателя.
Это функциональная основа интерфейса; отдельная визуальная доработка отложена
и не является условием его работоспособности.

Для показа не нужно вводить OID или команды SNMP:

1. Выберите «Рост загрузки процессора» и нажмите «Запустить».
2. Таблица и график показывают рост `cpu_usage` с 15 до 90. В списке над графиком
   можно выбрать другой числовой показатель. Для «Скачка температуры» выберите
   «Температура»: через 5 секунд значение изменится с 35 до 80.
3. Адрес, UDP-порт и community берутся из устройства и отображаются под кнопками.
   После завершения сценария агент продолжает отвечать с последними значениями.
   Счётчик сценария останавливается на его длительности (например, `20 / 20 с`),
   а отдельный счётчик работы эмулятора продолжает расти. График после окончания
   сценария показывает сохранённое значение во времени работы эмулятора.
4. Нажмите «Остановить», выберите другой пример и запустите его. Новый запуск
   восстанавливает начальные значения. Закрытие окна также останавливает агент
   и освобождает порт; окно закрывается после завершения фоновой работы.

Два режима разделяют демонстрацию и работу со своими конфигурациями:
«Готовый пример» показывает только список демонстраций, «Свои JSON-файлы» —
пути устройства и сценария с кнопками «Выбрать файл…». Переключение режимов
сохраняет пользовательские пути; выбор примера их не перезаписывает.
Проверку любой пары выполняет общий `load_json_config`, как в CLI.
Файлы в панели не редактируются. Название демонстрации внутри JSON не требуется.
Ошибки чтения, конфигурации и занятого порта отображаются в окне. Пока агент
работает, выбор профиля и повторный запуск заблокированы. Снимки значений
обновляются примерно каждые 100 мс; график хранит последние 600 снимков (около
60 секунд), поэтому при более частых изменениях не отображает каждый тик.
CLI и внешние SNMP-клиенты продолжают работать; для одновременного запуска
нескольких экземпляров нужны разные порты.

Для независимой проверки запущенной панели можно использовать команды GET/WALK
из раздела демонстрации ниже. Автоматические проверки жизненного цикла и
совпадения показателей с SNMP находятся в `tests/test_gui_controller.py`;
`tests/test_gui.py` проверяет настоящее окно. На Linux для этих окон нужен
дисплей или `xvfb-run -a`; CI запускает их с виртуальным дисплеем и не допускает
пропуска GUI-проверок. `tests/gui_smoke.py` проверяет окно и GET/WALK для
установленного пакета.

### Готовые устройства

В каждом JSON-устройстве от 5 до 10 метрик, включая `Integer32` и `OctetString`.
Все примеры используют демонстрационные OID в ветке `1.3.6.1.4.1.55555`,
адрес `127.0.0.1:1161` и community `public`. Это учебные профили, а не MIB
конкретных производителей. Одновременно на одном порту запускается один профиль.

| Устройство | Метрик | Устройство JSON | Сценарий JSON | Показ |
|---|---:|---|---|---|
| Базовое устройство | 5 | `examples/device.json` | `stable.json`, `temperature-jump.json`, `cpu-step.json` | Стабильные значения, скачок температуры, рост CPU |
| Коммутатор | 7 | `examples/switch-device.json` | `examples/switch-traffic.json` | Рост входящего/исходящего трафика и загрузки CPU |
| ИБП | 8 | `examples/ups-device.json` | `examples/ups-battery.json` | Переход на батарею, снижение заряда и запаса работы |

У коммутатора доступны CPU, температура, описание, число портов, активные
порты, входящий и исходящий трафик. За первые 9 секунд CPU повышается с 25 до
70%, трафик — со 120 до 600 и с 80 до 440 Мбит/с. Остальные показатели
сохраняются. Сценарий длится 20 секунд с интервалом 1 секунда.

У ИБП доступны заряд, нагрузка, входное и выходное напряжение, запас работы,
температура батареи, описание и источник питания. Сразу при запуске сценария
источник переключается с `mains` на `battery`, входное напряжение — с 230 на
0 В. Каждые 2 секунды заряд снижается на 10 пунктов до 20%, запас работы —
на 3 минуты до 6 минут. Пределы достигаются через 16 секунд; выходное
напряжение остаётся 230 В. Полная длительность — 20 секунд.

Оба новых профиля доступны в режиме «Готовый пример». В консоли OID и имена
метрик подсказываются из выбранного устройства. После завершения сценария
последние значения остаются доступны по SNMP до остановки.

Запуск из CLI:

```powershell
uv run --locked snmp-emulator --device-config examples/switch-device.json --scenario examples/switch-traffic.json
uv run --locked snmp-emulator --device-config examples/ups-device.json --scenario examples/ups-battery.json
```

Команды запускаются по очереди; перед второй остановите первую через Ctrl+C.

### Показ SNMP-запросов

После запуска эмулятора нажмите **«SNMP-запросы…»**. Откроется отдельная
консоль. Она отправляет настоящие SNMP v2c-пакеты по UDP на адрес и порт
запущенного устройства, используя его community. Для `0.0.0.0` клиент
обращается к `127.0.0.1`. WSL, Net-SNMP и отдельная установка клиента для этого
пути не нужны; внешние клиенты по-прежнему можно использовать независимо.

Кнопки **GET**, **GETNEXT**, **WALK**, **GETBULK**, **HELP** и **CLEAR** подставляют
готовую команду. Для SNMP подставляется OID текущей конфигурации; локальным
командам HELP/CLEAR аргументы не нужны. Нажмите Enter или «Выполнить».
HELP и CLEAR работают также при остановленном эмуляторе.

| Команда | Что демонстрирует |
|---|---|
| `GET cpu_usage` | Значение конкретной метрики по имени или её OID |
| `GETNEXT 1.3.6.1.4.1.55555.1` | Первую метрику после указанного OID |
| `WALK 1.3.6.1.4.1.55555.1` | Обход ветки последовательными GETNEXT |
| `GETBULK 1.3.6.1.4.1.55555.1 5` | До пяти следующих значений одним GETBULK, non-repeaters=0 |

В SNMP нет отдельной операции GETWALK: WALK — процедура клиента. Для удобства
принимается псевдоним `GETWALK`. Также доступны `snmpget`, `snmpgetnext`,
`snmpwalk`, `snmpbulkget` с тем же коротким синтаксисом; параметры оболочки
Net-SNMP (`-v`, `-c` и другие) здесь не используются.

При вводе команды список под строкой предлагает доступные OID и имена метрик
из работающего устройства. Можно нажать на подсказку или вставить первую
клавишей Tab. В пустой строке список предлагает все шесть основных команд;
после GET/GETNEXT/WALK/GETBULK — подходящие OID. Он показывает четыре строки
за раз и прокручивается колёсиком или вертикальной полосой справа; остальные
подсказки не отбрасываются. ↑/↓ в строке ввода возвращают предыдущие команды.
OID допускается ввести
вручную: например, `GET 1.3.6.1.4.1.55555.99.0` показывает стандартный ответ
`NoSuchObject`, GETNEXT после последней метрики — `EndOfMibView`.
В ответе выводятся OID, тип, значение, адрес назначения и длительность запроса.
`HELP` выводит справку, `CLEAR` очищает видимую историю ответов.
Остановка и повторный запуск не стирают предыдущие ответы: консоль добавляет
отметки времени, номер сеанса, имена файлов профиля и сообщения о состоянии.
Номер сеанса увеличивается при каждом новом запуске, в том числе при запуске
того же профиля. Если запрос предыдущего сеанса ещё завершается, новый запуск
доступен после его окончания или отмены, чтобы ответы не смешивались.

Запросы выполняются в фоне. «Отменить» прерывает обход; таймаут одного ответа —
1 секунда без повторов, общее ограничение — 15 секунд, WALK — до 256 метрик,
GETBULK — от 1 до 50 повторений (по умолчанию 5). Закрытие окна консоли
отменяет запрос и сохраняет историю до закрытия приложения. Остановка агента
и закрытие главного окна также отменяют запрос; приложение дожидается
завершения сетевого клиента. Консоль показывает ответы сети, таблица и график
основной панели — снимки хранилища; значения могут различаться, если между
обновлением таблицы и запросом произошёл следующий тик сценария.

## Формат устройства

Оба файла — UTF-8 JSON без BOM. В `agent` задаются IPv4-адрес `host`, UDP-порт
`port` (1–65535, по умолчанию 1161) и непустая строка `community`. Если поля
пропущены, используются `0.0.0.0`, `1161`, `public`. Объект `agent` обязателен.

```json
{
  "agent": {"host": "127.0.0.1", "port": 1161, "community": "public"},
  "metrics": [
    {"name": "cpu", "oid": "1.3.6.1.4.1.55555.1.1.0", "type": "Integer32", "initial": 15},
    {"name": "status", "oid": "1.3.6.1.4.1.55555.1.2.0", "type": "OctetString", "initial": "OK"}
  ]
}
```

У метрики обязательны `name`, `oid`, `type`, `initial`. Необязательное поле
`access` допускает только `read-only`. Имена после удаления крайних пробелов
должны быть непустыми и уникальными. OID — числовые компоненты, разделённые
точками; разрешена одна начальная точка. Начальная точка и ведущие нули
нормализуются, поэтому `.01.3.6` и `1.3.6` считаются одним OID.

`Integer32` имеет диапазон −2147483648…2147483647. Старое имя `Integer`
принимается как псевдоним того же типа; проверка и кодирование SNMP общие.
`OctetString` принимает строку UTF-8, максимум 65535 байт. Сохраняются типы
`ObjectIdentifier`, `IpAddress`, `Counter32`, `Gauge32`, `TimeTicks`, `Counter64`.
Числовые строки, дробные и логические значения не заменяют целое число.

## Формат сценария

```json
{
  "duration": 20,
  "update_interval": 1,
  "rules": [
    {"type": "step", "oid": "1.3.6.1.4.1.55555.1.1.0", "step": 10, "limit": 90}
  ]
}
```

`duration` и `update_interval` — положительные конечные числа в секундах.
В `rules` нужна хотя бы одна запись. Каждое правило ссылается на метрику по
нормализованному `oid`; на один OID допускается одно правило. Метрики без
правил сохраняют `initial`.

| `type` | Остальные поля | Поведение |
|---|---|---|
| `constant` | `value` | Устанавливает значение при старте и сохраняет его |
| `jump` | `at`, `value` | Сохраняет `initial` до `at`, затем устанавливает `value` |
| `step` | `step`, `limit` | Начинает с `initial`, каждый интервал прибавляет шаг и ограничивает результат пределом |

`constant` и `jump` принимают значения целевого SNMP-типа, включая строки.
Для `jump` требуется `0 <= at <= duration`. `step` предназначен для числовых
метрик: шаг — ненулевое целое число, предел должен лежать по направлению шага
от начального значения и внутри диапазона типа. Отрицательный шаг поддержан,
например `step: -3, limit: -1` при `initial: 10` даёт 10, 7, 4, 1, −1, −1.

Обновления выполняются в моменты `0`, `update_interval`, `2 * update_interval`
и далее до `duration` включительно. Скачок между тиками применяется на первом
тике, не меньшем `at`. Если такого тика до конца сценария нет, значение не
меняется. Если длительность не кратна интервалу, сохраняется результат
последнего полного тика. Например, при длительности 0.35 и интервале 0.1
последний тик — 0.3. Расчёт опирается на монотонное время и десятичную
арифметику; задержки планировщика не накапливаются. При задержке выполняется
актуальный тик без воспроизведения промежуточных состояний.

После `duration` сценарий прекращает обновления, но агент продолжает отвечать
с последними значениями до остановки процесса. Новый запуск загружает `initial`.

Неизвестные поля, повторные JSON-ключи, дубли имён/OID, неверные типы, значения,
правила и ссылки отклоняются до создания приложения. Ошибки чтения, UTF-8,
JSON и конфигурации завершают CLI кодом 2 с диагностикой без traceback.

## Демонстрация

`examples/device.json` содержит пять метрик: CPU=15, температура=35,
описание устройства, память=40 и статус=OK. Запускайте по одному сценарию:

```bash
uv run --locked snmp-emulator --device-config examples/device.json --scenario examples/stable.json
uv run --locked snmp-emulator --device-config examples/device.json --scenario examples/temperature-jump.json
uv run --locked snmp-emulator --device-config examples/device.json --scenario examples/cpu-step.json
```

| Сценарий | Ожидаемый результат |
|---|---|
| `stable.json` | Все значения постоянны, длительность 30 с |
| `temperature-jump.json` | Температура 35 → 80 на 5-й секунде, длительность 20 с |
| `cpu-step.json` | CPU 15, 25, 35, …, 85, 90 с шагом раз в секунду; 90 с 8-й секунды, длительность 20 с |

В другом терминале используйте Net-SNMP (`snmpget`, `snmpwalk`):

```bash
snmpget -v2c -c public -On 127.0.0.1:1161 1.3.6.1.4.1.55555.1.1.0
snmpget -v2c -c public -On 127.0.0.1:1161 1.3.6.1.4.1.55555.1.2.0
snmpwalk -v2c -c public -On 127.0.0.1:1161 1.3.6.1.4.1.55555
snmpget -v2c -c public -On 127.0.0.1:1161 1.3.6.1.4.1.55555.99.0
```

GET возвращает `INTEGER: 15` для начального CPU и `INTEGER: 35` для температуры;
повторите запрос после указанного времени. WALK возвращает пять OID.
Неизвестный OID возвращает `No Such Object`, после последнего OID GETNEXT
возвращает `endOfMibView`. После 20 с CPU/температура сохраняют последнее значение.
Остановите процесс, запустите его снова и сразу запросите метрики: начальные
значения восстановятся. Неверная community приводит к тайм-ауту.

## Совместимость с YAML

Старый CLI и расширенные сценарии сохраняются:

```bash
uv run --locked snmp-emulator --config examples/device.yaml --check-config
uv run --locked snmp-emulator --config examples/overload.yaml
```

`--config` нельзя смешивать с JSON-аргументами. YAML использует `schema_version: 1`,
`agent`, `metrics`, `scenarios`. Внутренние действия `set`, `sequence`, `ramp`,
`step`, ссылки по имени метрики и `repeat_every` продолжают работать.
Примеры полного формата — `examples/device.yaml` и `examples/overload.yaml`.


завершение сценариев, сохранение значений и восстановление начальных.
В Linux дополнительно выполняется проверка примеров командами Net-SNMP.

## Ограничения

SNMP SET, traps, SNMP v3, импорт MIB и несколько устройств в одном процессе
не поддерживаются. Журналирование каждого изменения метрики относится к
отдельной задаче 02; этот выпуск сохраняет существующее журналирование запуска,
остановки и ошибок исполнения.
