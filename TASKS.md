# Текущие задачи

## Этап 1. JSON-конфигурация и запуск

### 01. Конфигурация устройства в JSON

**Цель:** выделить описание устройства из общего YAML-файла в отдельный
JSON-файл.

Нужно:

- создать отдельную Pydantic-модель конфигурации устройства;
- сохранить параметры агента: адрес, порт и community string;
- описать список метрик с полями `name`, `oid`, `type` и `initial`;
- читать файл как UTF-8 JSON;
- запрещать неизвестные поля;
- обнаруживать повторяющиеся JSON-ключи;
- оставить текущую внутреннюю модель метрик пригодной для расширенных SNMP-типов.

**Критерий готовности:** корректный файл загружается независимо от сценария, а
невалидный JSON, неизвестное поле, неверный OID и повторяющийся ключ дают
понятную конфигурационную ошибку до запуска UDP-агента.

**Зависимости:** нет.

### 02. Конфигурация сценария в JSON

**Цель:** выделить сценарий изменения метрик в самостоятельный JSON-файл.

Нужно:

- создать отдельную Pydantic-модель сценария;
- предусмотреть длительность сценария и интервал обновления;
- хранить ссылки на изменяемые метрики через OID;
- описать обязательные правила ТЗ: постоянное значение, скачок в заданный
  момент и пошаговое изменение до предела;
- сохранить возможность преобразования новой схемы в расширенные внутренние
  действия `set`, `sequence`, `ramp` и `step`;
- читать файл как UTF-8 JSON и отклонять неизвестные поля и повторяющиеся ключи.

**Критерий готовности:** файл сценария можно провалидировать отдельно на уровне
его собственной структуры, не запуская эмулятор.

**Зависимости:** нет.

### 03. Объединение устройства и сценария

**Цель:** собирать два внешних JSON-файла в существующую внутреннюю
конфигурацию приложения.

Нужно:

- добавить одну точку загрузки пары «устройство + сценарий»;
- связать правила сценария с метриками устройства;
- проверять дубли OID и имён метрик;
- отклонять ссылки на отсутствующие OID;
- проверять совместимость правила со SNMP-типом метрики;
- выполнять все проверки до создания `EmulatorApplication` и открытия порта.

**Критерий готовности:** приложение получает готовую внутреннюю модель только
после успешной проверки обоих файлов и всех связей между ними.

**Зависимости:** 01, 02.

### 04. Новый CLI-контракт

**Цель:** выбирать конфигурацию устройства и сценарий через командную строку.

Нужно:

- заменить единичный `--config` двумя явно названными аргументами;
- обновить `--check-config`, чтобы он проверял оба файла и связи между ними;
- сохранить `--version` и `--log-level`;
- выдавать понятную ошибку при отсутствии любого обязательного пути;
- не открывать UDP-порт в режиме проверки конфигурации.

Рекомендуемые имена аргументов: `--device-config` и `--scenario`. Если будут
выбраны другие имена, их нужно одинаково использовать в коде, тестах, CI и
README.

**Критерий готовности:** эмулятор запускается выбранной парой JSON-файлов, а
режим проверки завершается до создания сетевого агента.

**Зависимости:** 03.

## Этап 2. Совместимость схемы с ТЗ

### 05. Тип `Integer32`

**Цель:** принимать точное название SNMP-типа из ТЗ.

Нужно:

- добавить `Integer32` во внешнюю JSON-схему;
- преобразовывать его в `pysnmp.proto.rfc1902.Integer32`;
- проверять допустимый знаковый 32-битный диапазон;
- решить вопрос совместимости со старым внутренним названием `Integer` без
  дублирования логики кодирования;
- добавить проверки минимального, максимального и выходящего за диапазон
  значений.

**Критерий готовности:** метрика типа `Integer32` проходит конфигурационную
проверку, корректно отвечает по SNMP и отклоняет значение вне диапазона.

**Зависимости:** 01.

### 06. Ссылки сценариев на метрики по OID

**Цель:** убрать зависимость внешнего сценария от внутренних имён метрик.

Нужно:

- находить метрику сценария по OID;
- нормализовать OID перед сравнением;
- обнаруживать отсутствующий OID до запуска;
- разрешать числовые правила только для числовых SNMP-типов;
- сохранить имя метрики во внутренней модели там, где оно удобно для текущего
  движка и логов.

**Критерий готовности:** все правила из JSON-сценария связываются с устройством
по OID, а отсутствующая или несовместимая метрика приводит к понятной ошибке.

**Зависимости:** 02, 03, 05.

### 07. Длительность и интервал обновления сценария

**Цель:** реализовать временную модель, заданную в ТЗ.

Нужно:

- передавать `duration` и `update_interval` из JSON в движок;
- применять изменения независимо от поступления SNMP-запросов;
- не вычислять новые значения после окончания сценария;
- сохранять последнее достигнутое значение до завершения процесса;
- исключить накопление ошибки времени на дробных интервалах;
- сохранить детерминированные тесты через абстракцию часов.

**Критерий готовности:** сценарий обновляется с заданным интервалом, прекращает
изменения после `duration`, а последнее значение продолжает возвращаться через
SNMP.

**Зависимости:** 02, 03.

### 08. Адаптер обязательных правил сценария

**Цель:** поддержать точные правила ТЗ, не отказываясь от уже готового
расширенного сценарного движка.

Нужно:

- преобразовывать постоянное значение во внутреннее действие;
- преобразовывать скачок в заданный момент во внутреннее действие;
- преобразовывать шаг с интервалом и пределом во внутреннее действие;
- корректно обрабатывать положительный и отрицательный шаг;
- гарантировать, что значение не пересекает заданный предел;
- не удалять существующие `sequence` и `ramp`: они остаются внутренними или
  расширенными возможностями проекта.

**Критерий готовности:** три обязательных вида сценариев полностью выражаются
через новую JSON-схему и выполняются существующим движком.

**Зависимости:** 05, 06, 07.

## Этап 3. Журналирование

### 09. Журналирование изменений метрик

**Цель:** фиксировать фактические изменения значений во время работы сценария.

Нужно:

- писать запись только при реальном изменении значения;
- включать в запись имя метрики, OID, старое и новое значение;
- по возможности указывать сценарий или правило, вызвавшее изменение;
- использовать стандартный модуль `logging` и общий формат с отметкой времени;
- не создавать одинаковую запись на каждом тике после достижения предела.

**Критерий готовности:** по журналу можно восстановить, когда и как менялась
метрика, без повторяющегося шума от неизменившихся значений.

**Зависимости:** 08.

### 10. Журналирование конфигурационных ошибок

**Цель:** выводить ошибки устройства и сценария через настроенное
журналирование с отметкой времени.

Нужно:

- настраивать logging до загрузки конфигурации;
- заменить прямую печать конфигурационных ошибок в `stderr` на `LOGGER.error`;
- сохранить ненулевой код завершения;
- не выводить traceback для ожидаемой пользовательской ошибки;
- различать ошибку чтения файла, ошибку JSON, ошибку схемы и ошибку связи
  сценария с устройством.

**Критерий готовности:** любая ожидаемая конфигурационная ошибка содержит время,
уровень и понятное описание, а процесс завершается без запуска агента.

**Зависимости:** 04.

## Этап 4. Демонстрационные конфигурации

### 11. Конфигурация устройства с 5–10 метриками

**Цель:** подготовить основной профиль устройства для демонстрации и приёмки.

Нужно:

- создать JSON-файл устройства с 5–10 уникальными OID;
- обязательно использовать `Integer32` и `OctetString`;
- включить метрики, подходящие для трёх сценариев, например температуру и
  загрузку процессора;
- подобрать понятные начальные значения;
- убедиться, что весь набор корректно обходится через `snmpwalk`.

**Критерий готовности:** файл проходит `--check-config` с каждым обязательным
сценарием и даёт связный результат SNMP-обхода.

**Зависимости:** 01, 03, 05, 06.

### 12. Сценарий стабильных значений

**Цель:** подготовить обязательный сценарий без изменения наблюдаемых метрик.

Нужно:

- создать отдельный JSON-файл;
- использовать правило постоянного значения;
- выбрать понятную длительность и интервал обновления;
- проверить, что повторные `snmpget` возвращают одинаковое значение.

**Критерий готовности:** сценарий проходит проверку и демонстрирует стабильное
значение на всём интервале работы.

**Зависимости:** 08, 11.

### 13. Сценарий скачка температуры

**Цель:** подготовить обязательный сценарий однократного изменения температуры.

Нужно:

- создать отдельный JSON-файл;
- сослаться на температурную метрику по OID;
- задать начальное значение, момент скачка и новое значение;
- проверить сохранение нового значения после скачка и после окончания сценария.

**Критерий готовности:** до заданного момента SNMP возвращает исходную
температуру, после него — новое значение, которое сохраняется до остановки
эмулятора.

**Зависимости:** 08, 11.

### 14. Сценарий ступенчатой загрузки CPU

**Цель:** подготовить обязательный сценарий пошагового изменения до предела.

Нужно:

- создать отдельный JSON-файл;
- сослаться на метрику CPU по OID;
- задать шаг, интервал обновления и верхний предел;
- проверить отсутствие переполнения и остановку изменения на пределе;
- проверить сохранение достигнутого значения после окончания сценария.

**Критерий готовности:** последовательные запросы показывают ступенчатый рост,
значение достигает предела, не превышает его и затем остаётся постоянным.

**Зависимости:** 08, 11.

## Этап 5. Проверки, упаковка и документация

### 15. Тесты JSON-конфигурации и CLI

**Цель:** зафиксировать новый внешний контракт отдельным набором тестов.

Нужно проверить:

- успешную загрузку пары файлов;
- отсутствующий или нечитаемый файл;
- неверный JSON и повторяющиеся ключи;
- неизвестное поле;
- дубли имён и OID;
- неверный тип или начальное значение;
- ссылку сценария на отсутствующий OID;
- несовместимое правило для `OctetString`;
- работу новых CLI-аргументов и `--check-config`.

**Критерий готовности:** ошибки контракта обнаруживаются до запуска приложения и
проверяются по смыслу, а не только по факту исключения.

**Зависимости:** 01–06, 10.

### 16. Тесты сценариев, журналирования и перезапуска

**Цель:** зафиксировать runtime-поведение из ТЗ.

Нужно проверить:

- независимость изменения метрик от SNMP-запросов;
- постоянное значение, скачок и шаг до предела;
- соблюдение `duration` и `update_interval`;
- сохранение последнего значения после завершения сценария;
- восстановление начальных значений после создания нового процесса или
  экземпляра приложения;
- отсутствие дублирующихся записей об одном и том же значении;
- наличие времени и необходимых полей в логах.

**Критерий готовности:** ключевые временные проверки выполняются быстро и
детерминированно без реального ожидания длинных интервалов.

**Зависимости:** 07–10.

### 17. Упаковка примеров и CI

**Цель:** сделать новые JSON-файлы частью проверяемой поставки.

Нужно:

- обновить `MANIFEST.in` для JSON-примеров;
- проверить содержимое sdist и возможность использования примеров после
  установки wheel/sdist там, где это предусмотрено упаковкой;
- заменить YAML-команды в GitHub Actions;
- валидировать основное устройство со всеми тремя сценариями;
- сохранить Linux-матрицу Python 3.11–3.13 и Windows smoke;
- сохранить проверки Ruff, lock-файла, сборки и метаданных.

**Критерий готовности:** CI проверяет новый формат, все три сценария и
установленные дистрибутивы; YAML-пример больше не является единственной
приёмочной конфигурацией.

**Зависимости:** 04, 11–16.

### 18. Обновление README

**Цель:** привести пользовательскую документацию к фактическому интерфейсу.

Нужно:

- заменить YAML-примеры на два JSON-файла;
- описать установку и запуск;
- показать `--check-config`;
- кратко описать поля устройства и обязательные виды сценариев;
- привести команды `snmpget` и `snmpwalk` для демонстрационного устройства;
- описать ожидаемое изменение значений и сброс после перезапуска;
- отделить обязательные возможности ТЗ от дополнительных GETBULK и расширенных
  внутренних действий.

**Критерий готовности:** новый участник может установить проект и повторить
демонстрацию, используя только README и файлы из `examples`.

**Зависимости:** 04–17.

### 19. Финальный демонстрационный прогон

**Цель:** проверить проект как готовый результат, а не только набор модулей.

Нужно выполнить и зафиксировать:

- проверку каждой пары устройство/сценарий через CLI;
- запуск эмулятора с каждым из трёх сценариев;
- `snmpget` известного OID;
- `snmpwalk` всего демонстрационного дерева;
- запрос неизвестного OID и стандартный ответ SNMP;
- наблюдение постоянного значения, скачка температуры и ступенчатого CPU;
- остановку и повторный запуск с восстановлением начальных значений;
- полный запуск тестов и проверок качества.

Результат можно оформить небольшим разделом в README или отдельным текстовым
чек-листом с командами и ожидаемыми результатами. Не нужно добавлять в
репозиторий временные логи и машинно-зависимые пути.

**Критерий готовности:** демонстрация воспроизводится по сохранённым командам, а
фактическое поведение совпадает с ТЗ.

**Зависимости:** 17, 18.

## После обязательных задач

До завершения задач 01–19 не планируются новые функции, не требуемые ТЗ. В
частности, сейчас не нужны SNMP SET, traps, SNMP v3, GUI, импорт MIB, база данных
или одновременная эмуляция нескольких устройств.

После финального прогона отдельно можно решить, нужны ли дополнительные
улучшения и какие из них действительно полезны проекту.
